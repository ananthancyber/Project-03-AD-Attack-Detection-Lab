# 1. Attack Simulation Overview

This document records the controlled authentication activity performed during Day 07 of the Active Directory Attack & Detection Lab.

The objective was to simulate a scenario in which a valid domain account authenticates to a Windows system from an unexpected workstation.

The simulation used a dedicated test account:

`CORP\pt_test`

The account was first used from the normal Windows client to establish an authentication baseline.

The same account was then used from the Kali Linux host to perform controlled SMB authentication.

This created the following behavioral comparison:

### Normal Authentication

`CORP\pt_test → WIN10-CLIENT → NTLM`

### Simulated Suspicious Authentication

`CORP\pt_test → KALI → NTLM`

The purpose of the simulation was not to demonstrate credential theft.

Instead, it was designed to generate authentication telemetry that a SOC analyst could investigate and detect.

---

# 2. Simulation Objective

The primary objectives were:

1. Establish a normal NTLM authentication baseline.
2. Verify SMB connectivity between the lab systems.
3. Create a dedicated test identity.
4. Perform controlled authentication from Kali Linux.
5. Generate Windows Security Event ID `4624`.
6. Generate Domain Controller Event ID `4776`.
7. Identify the originating workstation and source IP.
8. Compare the suspicious authentication against the normal baseline.
9. Validate the resulting Blue Team detection.
10. Produce evidence suitable for SOC investigation and documentation.

# 4. Threat Scenario

The simulated scenario represents a domain account being used from a workstation that is not part of its normal authentication pattern.

In a real environment, this behavior could occur for several reasons.

### Potential malicious explanation

An attacker who has obtained valid credentials may attempt to use those credentials from another host.

### Potential legitimate explanation

The same behavior can also occur because of:

- Administrative activity
- Help-desk operations
- Service accounts
- Legacy applications
- Backup infrastructure
- Monitoring systems
- Newly deployed workstations
- Authorized security testing

Therefore, the simulation focuses on the **observable authentication anomaly**, not on assuming malicious intent.

# 30. Security Interpretation

The simulation demonstrates a change in authentication context.

The account and protocol remained the same:

`pt_test + NTLM`

The source changed:

`WIN10-CLIENT → KALI`

This is important because attackers who obtain valid credentials may attempt to use those credentials from systems that are not normally associated with the account.

However, the same behavior can have legitimate explanations.

Therefore, the correct Blue Team interpretation is:

**Suspicious authentication requiring investigation**

rather than:

**Confirmed account compromise**

# 31. What the Simulation Proves

The controlled experiment successfully demonstrates:

- NTLM authentication can be generated through SMB.
- Windows records successful network authentication as Event ID `4624`.
- Logon Type `3` identifies the observed network logon.
- Event ID `4624` can provide source workstation and source IP information.
- The Domain Controller records credential validation through Event ID `4776`.
- Event ID `4776` can identify the source workstation.
- Successful credential validation can be identified using Error Code `0x0`.
- Event ID `4624` and Event ID `4776` can be correlated.
- Authentication behavior can be compared against an established baseline.
- Unexpected-source authentication can be detected using repeatable queries.

The purpose of the simulation was to generate and investigate authentication telemetry.

# 35. Operational Security Considerations

In a production environment, an unexpected NTLM authentication should not automatically result in account containment.

The analyst should first determine:

- Whether the source is authorized
- Whether the account normally authenticates from that host
- Whether the source is an administrative system
- Whether the account is privileged
- Whether additional suspicious activity exists
- Whether multiple systems were accessed

The detection should therefore be used as an investigation trigger.
